## Business scope

The platform reconciles three fictional industrial ERPs while keeping organizations, establishments, products and customer/supplier roles distinct. A steward can inspect candidate evidence, see proposed attribute survivorship, request a merge or separation, and follow approval and execution under three distinct named roles. Source identities survive changes in the golden interpretation.

The implementation includes immutable source assertions; a standardized comparison projection; deterministic and conservative fuzzy evidence; whole-group compatibility checks; attribute-level authority and provenance; business-valid and knowledge histories; stable golden identifiers; merge, split and unmerge decisions; a transactional outbox; and a version-aware reporting projection. A correction publishes new events for consumers to reconcile.

The PostgreSQL reference is the transactional control plane. Five dbt models expose goldens, crosswalks, attribute lineage, quality and consumer impact. The Snowflake path publishes bounded versioned analytical snapshots and compares the full readback against PostgreSQL. It does not present Snowflake as a replacement for PostgreSQL's enforced transactional constraints.

## Included operational work

- A locked Python 3.12 package, checksummed migration, CLI and authenticated review console.
- A bounded single-host Compose reference with external secret files, persistent database state, loopback ingress and graceful shutdown.
- One durable application orchestrator, per-source checkpoints, bounded retries and explicit degraded-source behavior.
- Server-generated request/CLI correlation linked to durable run, decision, outbox and consumer identifiers; snapshot publication reports retain the warehouse query-ID boundary.
- Real-database tests for repeated ingestion, late corrections, conflicting versions, concurrent decisions, event replay, crash recovery and mistaken-merge correction after later source updates.
- Backup and restore procedures with a consistent snapshot, archive digest, exact fingerprints over 17 operational tables and post-restore invariants.
- Separate workflow definitions for PostgreSQL/container/browser qualification and Terraform provider-schema validation; dependency, licence-declaration and Git-history controls.
- Dedicated Snowflake Terraform resources with a generated provider lock, a small warehouse, concurrency/time bounds and a non-renewing warehouse-credit monitor.

## What the evidence establishes

Local execution covers source contracts, matching, survivorship, in-process API boundaries, provider adapter boundaries, dependency inventory/audit, static checks and a small synthetic candidate benchmark. The dbt PostgreSQL parse produced a genuine parse manifest. Actual values, command outcomes and limitations belong in the evidence index, not in an inferred overall pass.

The held-out corpus has 16 records and seven positive pairs. Both matching modes retrieve all seven positive pairs as candidates. Automatic matching yields three true pairs and zero false pairs, with recall of 3/7. Adding the bounded fuzzy review signal increases auto-plus-review recall from 6/7 to 7/7; one false review remains visible. These are synthetic fixture observations, not an industrial accuracy estimate.

## Unverified release gates

1. **PostgreSQL and deployment:** the local sandbox refuses socket creation. The first GitHub Actions run failed before a runner was assigned, leaving the PostgreSQL, dbt build/data tests, restore, load, container and rendered-console scenarios unexecuted. The exact admission failure remains unknown. An authorized runner capable of those processes is required.
2. **Terraform schema:** the official CLI formatted the configuration and installed the pinned Snowflake provider, generating the committed lock. Provider startup failed because it could not create a Unix socket. Schema validation, plan and apply are not established.
3. **Snowflake:** a dedicated authorized account, key-pair role, database/warehouse scope and explicit budget are required. No provider integration, warehouse timing, total credit charge or invoice is claimed.
4. **Repository publication:** the maintainer must explicitly choose the repository licence. Description/topics are prepared in [repository metadata](../repository-metadata.json) but have not been applied because the connected interface does not expose repository settings. Rulesets were unavailable on the current private plan, and branch-protection reads were denied to the integration. Public visibility and anonymous verification remain separately authorized actions.

## Known limits

The graph mutation lane is serialized under a PostgreSQL advisory lock. Candidate pairs are materialized in memory and dense blocks fail at explicit limits. The bounded synthetic profile does not demonstrate horizontal write scaling or representative database performance. Historical rows and full analytical snapshots grow with source assertions and corrections.

SQL, input, retry and workflow time bounds cover different stages. The Python orchestrator has no global wall-clock deadline; the operating procedure supplies an external process timeout and resumes durable checkpoints after interruption. API latency and runtime resource distributions remain unmeasured.

Future-effective assertions require an activation policy and are currently rejected. An update that makes an accepted group incompatible is rejected atomically until a steward separates the group. The reference database bootstrap account is not a production least-privilege role design. Off-host backup scheduling, secret rotation and remote TLS ingress need a target operating environment.

No screenshot, restored database, live warehouse result or release acceptance is fabricated to fill an execution gap. The implementation remains on the review branch until its actual integration results can be assessed.
