## Business scope

The platform reconciles three fictional industrial ERPs while keeping organizations, establishments, products and customer/supplier roles distinct. A steward can inspect pair evidence and proposed attribute survivorship, request a merge or separation, and follow approval and execution under three distinct named roles. Source identities survive changes in their golden interpretation.

The implementation includes immutable source assertions, standardized comparison projections, deterministic and conservative fuzzy evidence, whole-group compatibility, attribute authority/provenance, business and knowledge histories, stable golden IDs, merge/split/unmerge, a transactional outbox and a version-aware reporting consumer. A correction publishes new events; it does not undo external business transactions.

PostgreSQL is the transactional control plane. Five dbt models expose goldens, crosswalks, attribute lineage, quality and consumer impact. The separate Snowflake publisher is designed to validate full versioned analytical snapshots before activation. It remains unqualified against a live Snowflake account.

## Qualification-driven corrections

The continuation found and fixed two lifecycle gaps and their presentation consequence:

- A run now drains publication in bounded batches before persisting completion. No-progress and batch-budget failures retain durable progress for retry. Older incomplete terminal results reuse their run identity/checkpoints within the three-attempt limit.
- Merge preview, request, execution and automatic reconciliation share the same historical interval interpretation as golden reconstruction. An earlier identifier conflict is explained and blocks only the affected group, while unrelated matches continue.
- Candidate disposition is recomputed when another group member changes, and current/historical group conflicts are visible in console evidence. A snapshot cannot keep a stale group-conflict status after its cause disappears.

The changes add thirteen real PostgreSQL regressions. They introduce no SQL migration, identity-policy relaxation or dependency change. Existing already-complete run results retain their replay behavior; new publication counters describe the current attempt. The operating documentation and an optional alert's annotations now describe `mdm_unconsumed_events` correctly as reporting-consumer lag; the alert expression, name, duration and severity are unchanged, and no monitoring deployment is implied.

A later CI review corrected two evidence gaps: documentation generation no longer overwrites the executed dbt build results, and the populated-target restore control now requires the exact rejection instead of any nonzero exit. Selected revised workflow commands were [executed natively](../../evidence/2026-11-14/ci-evidence-hardening/qualification.json): 41 dbt tests passed again, build files survived docs unchanged, and two unrelated restore failures were correctly rejected. Both databases' 17 operational table fingerprints remained unchanged. The Snowflake helper's output paths were likewise separated, with live execution still pending.

## Practical limits

The graph mutation lane is serialized. Candidate pairs are materialized in memory and dense blocks fail at explicit limits. Historical rows and complete analytical snapshots grow with source assertions and corrections. A 300-source fixture does not establish enterprise capacity or horizontal write scaling.

The benchmark's Python heap covers matching; RSS is sampled before the database branch. These are not PostgreSQL server-memory peaks. The measured SQL plan is one query on a small fixture. HTTP checks establish behavior, not a latency service level or resource distribution.

Statement, lock, input, batch, retry and workflow bounds have different scopes. The Python orchestrator has no global wall-clock deadline; the operating procedure supplies an external process timeout and resumes checkpoints after interruption. Future-effective assertions remain rejected pending an activation policy. Incompatible source changes remain atomic failures until a steward separates the group.

The reference database bootstrap account is not a production least-privilege design. Off-host backup scheduling, secret rotation, remote TLS ingress, representative load and live warehouse billing require the intended operating environment. The original backup archive is excluded from published evidence.
